# 絶景予報

自然現象の予測アプリ。夕焼け・朝焼け・星空・雲海・霧氷・ダイヤモンドダスト・虹の7現象について、
「今日はその現象が見られそうか」を、数値予報から独自スコアで判定する。
**個人利用のための道具**（不特定多数への予報提供は行わない）。

用語は使い分けている。**予報**は気象庁や ECMWF が発表しているもの、
**予測**はそれを材料にこのアプリが独自に点数を付けたもの。

## 特徴

- **8モデルのアンサンブル** — 気象庁MSM/GSM・ICON・ECMWF・ECMWF AI・GFS・
  英国気象局・ARPEGE の中央値を点数にする。
  **この中央値が個々のモデルより当たることは実データで検証済み**（下記）
- **ECMWF 51メンバーで「どれくらい動きうるか」を測る** — 初期値をわずかに変えた
  51通りの計算の散らばりから、点数が何点ずれそうかを出す。
  当日の推定 8.9点に対し実測誤差 9.5点で、**較正が取れていることを確認済み**（下記）
- **14日先まで** — 8日目以降はモデルが順に落ちる（気象庁MSM 4日／ARPEGE 5日／
  英国気象局 7日／ICON 8日／気象庁GSM 12日／ECMWF・GFS 15〜16日）。
  14日先に残るのは3つ。何本の中央値かを持ち回し、信頼度の判定に使う
- **信頼度 A / B / C** — 評価の帯は20〜25点間隔なので、点数が何点ずれそうかをその幅と比べる。
  A は評価がほぼ動かない（±10点未満）、B は1段変わり得る（±20点未満）、C は当てにならない。
  **3段階なのは実測で区別がついたのが3つだから**で、増やすと根拠のない境目を足すことになる。
  モデルが5本未満になる9日目以降は A を出さない
- **「なぜこのスコアか」** — 加点・減点の内訳を寄与順に表示。合計は必ず表示スコアと一致する
- **文献由来の閾値** — 出典のない数値を使わない（下記）
- **実況はアメダスの実測** — 測った値をそのまま出す。標高差のある観測点しか無ければ気温減率で直す
- **記録と校正** — 実際どうだったかを記録し、点数の当たり具合を測る。
  訊き方は現象で変える（雲海・霧氷・ダイヤモンドダスト・虹は「見えたか」、朝焼け・夕焼け・星空は「期待どおりか」）

## 判定の根拠

| 現象 | 出典 |
|---|---|
| 夕焼け・朝焼け | SunsetWx 特許 US10459119（気圧面別の最適湿度帯、可視距離式 `d[mile]=1.32√(高度ft)`）／薄明の色の観測研究 [JAMC 2026](https://doi.org/10.1175/JAMC-D-25-0206.1)（エアロゾル・視程との関連） |
| 星空 | 雲量・降水・月（輝面比×高度）・視程 ＋ Lorenz Light Pollution Atlas 2025（VIIRS 実測） |
| 雲海 | 宙畑・秩父の決定木（前日最高−当日最低 >10.2℃ かつ 風速 <0.85m/s） |
| ダイヤモンドダスト | 北海道立総合研究機構・旭川2シーズン観測（最低気温 ≤−15℃ で 16/19日＝84%） |
| 霧氷 | 蔵王の樹氷研究（気温 ≤−5℃・風速 1〜5m/s・過冷却水滴） |
| 虹 | 太陽高度 ≤42°・降水・直射日光（雨域の方角はモデル解像度では解けないため参考値） |

## 構成

静的3ファイル。ビルド不要・依存パッケージなし。

- `index.html` — UI
- `sorami-core.js` — スコアリング、天文計算、API クライアント
- `spots.js` — 絶景スポット33件（座標は OSM 名称照合＋国土地理院標高で確認済み）

iOS版は現在作っていないため、配信対象はこのWeb版だけ。過去のSwift実装は
`parity-test.mjs` の参照用に残している。

## Xの実景照合

検証地点は `validation-sites.mjs` に固定し、既存登録地点の座標・標高は `spots.js`、
新規地点は設定内の `coordinateSource`・`elevationSource` を参照する。
東京を拠点に、朝焼けは葛西臨海公園・片貝中央海岸・犬吠埼、夕焼けは
江ノ島（片瀬西浜）・稲村ヶ崎・大さん橋を使う。
`study-x-sightings.mjs --sites` で一覧、`--plan 開始日 終了日 出力JSON` で
全地点×全日の未確認台帳を作る。写真が見つからない日も台帳に残す。
確認・実行手順の正本は Vault の「ドメイン/開発/手順/02_絶景予測を直す」→「精度を測る」。
撮影場所・撮影日・朝夕・写真が確認済みの記録だけ採点する。過去気象で再計算する
参考点であり、当時表示した予報を復元するものではない。大気質は未取得。

## データ源

予報 [Open-Meteo](https://open-meteo.com/) ／ 大気組成 CAMS（Open-Meteo Air Quality）／ 実況 気象庁アメダス ／
光害 [Lorenz Light Pollution Atlas](https://djlorenz.github.io/astronomy/lp/) ／
地点検索 OpenStreetMap Nominatim ／ 標高 国土地理院

## 精度について

精度の問題を2つに分けて考えている。

### (a) 気象予報そのものの精度 — 検証済み

`study-combiner.mjs` が、発表済み予報のアーカイブと ERA5 再解析を各日の
日の入り・日の出の時刻で突き合わせる。14地点（札幌〜那覇）× 180日 = 4970標本。

**学習と検証を日付で分ける。** 全標本で各手法を比べて最良を選ぶと、
差が小さいときにノイズを実力と読む。前半（3〜6月・2982件）で偏り補正・重み・
最良単独モデルを決め、後半（6〜8月・1988件）だけで測る。

| 要素 | 中央値の検証MAE | 次点 | 現行比 |
|---|---|---|---|
| 上層の雲 | **13.64** | 刈込平均 14.27 | +4.6% |
| 中層の雲 | **12.10** | 刈込平均 12.10 | +0.0% |
| 下層の雲 | 16.64 | 刈込平均 16.55 | −0.5% |
| 降水 | 0.150 | 偏り補正→中央値 0.149 | −0.6% |

**どの要素でも中央値を 1% 以上上回る手法は無かった。** アンサンブルという設計は妥当。

### 中央値をどこで取るか — 差は無い（`study-aggregation.mjs`）

採点は非線形（三角カーブ・上限・見え率の掛け算）なので、
「モデルごとに採点してから中央値」と「変数ごとに中央値を取って1回採点」は一致しない。
星空・12地点・90日＝1056標本で比べた。

| | 平均絶対誤差 | 偏り | 評価が変わる |
|---|---|---|---|
| A 採点してから中央値（現行） | 10.73点 | +0.46 | 32% |
| B 変数の中央値で1回採点 | 11.10点 | +0.16 | 32% |

平均では A が良いが、**標本ごとにどちらが実況に近かったかを数えると A の勝率 51.3%
（z = 0.8）で偶然の範囲**。0.37点の差を実力と読んではいけない。

両者は per-sample では平均 3.94点・最大 39.3点も違い、0.5点未満しか違わないのは 26% だけ。
**大きく食い違うのに、どちらも系統的に近くはない。**

現行の A を続けるのは、測って勝ったからではなく、
B が「上層雲は晴れているモデル」と「下層雲が厚いモデル」の値を混ぜて
どのモデルも予想していない空を作りうるため。理由は理屈のほうにある。

学習だけで見ると別の結論が出る点が重要で、上層の雲では最良単独モデル（ARPEGE）が
学習 11.79 と中央値 10.95 に迫るのに、検証では 17.73 まで崩れる。
下層の雲の「ECMWF AI が中央値より良い」も検証では再現しない（+0.1%）。
以前このREADMEに書いていた順位は、選ぶのと測るのを分けていなかった。

全雲量だけは偏り補正で 4.5% 改善するが**採用していない**。
一様なずれは全部の日を同じだけ動かすので日ごとの順位が変わらず、
「どの日に見に行くか」は変化しない。ばらつき自体は減っていない。

この検証でカナダGEMを除外した（上層雲が平均4.2%・最大38%しか出ず、他モデルと
スケールが異なっていた）。除外により上層の雲の MAE が 14.35 → 13.09 に改善。

実行: `node study-combiner.mjs 180` ／ 要素別の内訳は `node verify.mjs 30`

**限界**: アーカイブ予報は概ね当日〜翌日のリードタイム。数日先の精度は測れていない。
ERA5 も観測そのものではなくモデル同化の産物で、雲量の不確かさは大きい。

### (a-2) 点数そのものの誤差と、信頼度の較正 — 検証済み

`verify-score.mjs` が、要素ではなく**スコアの誤差**を測る。10地点×61日＝610標本:

| | |
|---|---|
| 平均絶対誤差 | **9.5点** |
| 中央値 | 5.8点 |
| p90 | 26.1点 |
| 偏り | −1.2点（ほぼ無偏） |
| 20点以上ずれた割合（ランクが変わる） | 17% |

この数字が信頼度の意味を決めている。ランク境界は20〜25点間隔なので、
**予測誤差10点未満＝ランクは動かない＝信頼度「高」**とした。

アンサンブル側との照合: 正規分布なら IQR = 1.349σ、平均絶対誤差 = 0.798σ。
当日のアンサンブル IQR の中央値 15 から予測誤差 8.9点。上の実測 9.5点と**6%以内で一致**する。

実行: `node verify-score.mjs 60` / `node verify-ensemble.mjs` / `node test-ensemble.mjs`

### (a-3) 何日前の予測かで、どれだけ外れるか — 検証済み（星空）

`study-leadtime.mjs` が、`previous-runs-api` の「N日前に出した予測」と ERA5 を
突き合わせ、**スコアそのもの**の誤差をリードタイム別に出す。
8地点 × 40日 = 288標本（全6モデル×全リードが揃ったもの）。

| 何日前 | 平均絶対誤差 | 20点以上ずれ | 評価の区分がずれる |
|---|---|---|---|
| 当日 | 12.6点 | 22% | 38% |
| 1日前 | 11.9点 | 19% | 36% |
| 2日前 | 13.7点 | 26% | 37% |
| 3日前 | 16.0点 | 33% | 43% |
| 4日前 | 17.7点 | 36% | 47% |
| 5日前 | 18.7点 | 38% | 46% |

**当日〜2日前はほぼ同じで、劣化が始まるのは3日前から。** 5日前で誤差が5割増える。

アンサンブルが出している「点数が何点ずれそうか」を4地点で読むと
1〜5日前が 11.8 / 13.8 / 12.1 / 15.9 / 17.4 で、上の実測とよく一致する。
**日数ぶんの下駄は要らない**（アンサンブルが既に織り込んでいる）。

実行: `node study-leadtime.mjs 40`

**測れるようになった経緯**: 以前は「アンサンブルに過去アーカイブが無く、
`previous-runs-api` には雲の層別が無い」ため測れないとしていた。
前半は正しいが、後半は測れない理由になっていなかった。層別が無いのは夕焼け・朝焼けの話で、
星空は総雲量・降水・湿度だけで採点している。それらには過去実行がある。

**限界**:
- 夕焼け・朝焼けは層別の雲が要るので、この方法では測れないまま
- 気象庁MSMだけ過去実行が無い（7モデル中6モデルの中央値で測っている）
- ARPEGE は4日前より先の過去実行を持たないため除外
- 誤差には ERA5 側の誤差も含まれる。当日の 12.6点すべてが予測の誤りではない

**アンサンブルは点数を動かさない。** アンサンブル中央値は8モデル中央値より
平均13.2点低く出る（140標本）が、どちらが正しいかを検証する手段が無い。
検証できないものでスコアは動かさない。

### (b) 点数が実際の美しさと合うか — 未検証

閾値の骨格は上記の文献に基づくが、**配点・カーブの形・上限値は本アプリの判断であり
文献値ではない**。ここを検証するには人が空を見た記録が要る。記録機能はそのためにある。

## 注意

これは予報であって観測ではない。当日の空とは異なることがある。

**気象業務法**により、独自予報を反復・継続して他人へ提供するには気象庁長官の許可が要る。
本アプリは個人利用に留める。
